# UV-K10 Pro 广播存台、设置与证据

本实现限定 **UV-K10 Pro，协议型号 K8，参照固件 8.02.16**。K8 是该产品在官方编程协议和 APK 中的标识；不能据文件中的 `K7` .NET 命名空间名称改成另一个产品，也不能搬入 APK 其他产品配置。

这里的可写含义是“已经实现相应的文件字节编码和受控设备传输接口”。没有接入实机，不能等同于 USB、蓝牙、Si4732 或 BK1080 已完成硬件验收。

## 来源与方法

- 既有研究仓库：[uv-k10pro-firmware](https://github.com/guanzi008/uv-k10pro-firmware)，其中普通信道编解码代码为 MIT；本项目独立移植其算法。
- 官方 UV-K10 Pro CPS 0.56 主程序，SHA-256 `79c9b3429187f7fca13cc8971d0e5fd46184f078127f149f333a267b99815132`。本次通过 PE/.NET 元数据、固定数组 marshaling 和 IL 静态分析核对，未执行安装程序或 CLR 程序。
- 官方分发的 K8 APK 配置，64 包 K8 资产 SHA-256 `5df044c86a2a2eee8fd4b709bf47c1a6cfeb030b30d23c3010b09f19593dfc5f`；68 包对应 `7b8cb1c712251fd892101f3650571ecf8992d285f82b9518c730402e9909a2a5`。仅抽取存储事实作交叉检查。
- 固件参考明文镜像 SHA-256 `061759672cc69a1b00420ce6fae67b0756d3db111f8fa4329cadc940dcd17f17`；普通信道、亚音、扫描列表、RGB 亮度等继承研究仓库中的原函数重放证据。

仓库不分发这些厂商二进制、完整配置或原始反汇编。下面的 token/RVA 标识便于对照用户自行下载的同一 CPS 样本。

## 广播芯片与能力

| 芯片视图 | 本项目展示的频段 | 存储关系 | 证据边界 |
|---|---|---|---|
| Si4732 | FM、LW、MW、SW | 每个频段独立头部和记录数组 | CPS 活跃序列化及 stock CPU 读写路径均已确认；实机尚未验证 |
| BK1080 | FM | 与 Si4732 视图中的 FM 使用同一块存台数据 | CPS 移除 LW/MW/SW；stock CPU 在 BK1080 条件下强制选择 FM，不存在这里另造的 BK1080 私有地址 |

`param_string.GetRadioChipTypes`，token `060002CD` / RVA `0x4A6E4`，给出 BK1080 与 Si4732 选项；`main.UpdateFmTree`，`060003B0` / `0x66114`，体现频段能力差异。这里的视图切换不会修改实际硬件型号配置。

CPS 另有一个 160 字节的旧 `CpsFmConfigStruct` 类型（`0200008E`）。对本样本的方法体扫描未找到它或它的字段的活跃引用，所以没有拿它实现 BK1080 编解码。类型存在不等于当前产品使用它。

## 广播存储地图

偏移均相对于外部 NOR 的起点，**不是 MCU 更新镜像偏移**。整数采用小端。频率使用精确整数 Hz，存储整数单位为 10 Hz。

| 频段 | 头部地址 | 记录起点 | 记录数 | 用户预置数 | 已证 CPS 编辑范围 |
|---|---:|---:|---:|---:|---|
| FM | `0x12100` | `0x12108` | 33 | 32 | 76–108 MHz |
| LW | `0x12300` | `0x12308` | 33 | 32 | 150–520 kHz |
| MW | `0x12500` | `0x12508` | 33 | 32 | 520–1800 kHz |
| SW | `0x12700` | `0x12708` | 129 | 128 | 1.8–30 MHz |

每组 **记录 0 是 VFO，记录 1..32 或 1..128 是预置台**。这不是由数量推测：`wfm_fm.GridViewFmInit`，`060004C5` / `0x7A828`，明确把第 0 行标成 VFO，后续行标成 CHn。`CPS_FM_INFO` 的数组 marshal 数量为 33；`CPS_SW_INFO` 为 129。

`main.ConvertCpsFmParam`（`060003E0` / `0x68540`）从 `0x12100` 开始，以 `0x200` 的间隔加载前三组，然后加载 SW。`main.GetFmParam`（`06000401` / `0x69D48`）按相同地址序列写入，`0x12000` 单字节存当前广播频段枚举。

`wfm_progress.CpsReadFm` / `CpsWriteFm`（`060004F9` / `060004F8`）共同传输区间是 `[0x12000, 0x12B10)`，长度 `0xB10`。这段内的间隔字节也必须保留，不能把每组声明的长度当作可以清零整段的许可。

CPS 中确实存在一个 `64..108` 的 Si4732 范围常量，但当前 FM 转换器 `0600002A` 直接使用 `76..108`；编辑界面又分成 `76..88` 与 `88..108`。本项目默认编辑范围服从活跃 CPS 路径，不把未使用常量宣称成已验证能力。范围外的已有原始值仍可读取、备份和保持，不会自动夹限。

### 8 字节广播头

| 偏移 | 数据 | 编码 |
|---:|---|---|
| `+0` | 工作模式 | 0=VFO，1=信道 |
| `+1` | 当前信道 | 0 起算的预置索引，FM/LW/MW 为 0..31，SW 为 0..127 |
| `+2` | AGC | CPS 索引 0=自动开启，1..37=手动级别；没有断言 BK1080 使用此字段 |
| `+3` | FM 步进 | 索引 0/1/2 = 50/100/200 kHz |
| `+4` | AM 步进 | 索引 0/1/2 = 1/5/10 kHz |
| `+5` | SSB 步进 | 索引 0/1/2 = 1/5/10 kHz |
| `+6` | AM 带宽 | 索引顺序 6、4、3、2、1、1.8、2.5 kHz |
| `+7` | SSB 带宽 | 索引顺序 1.2、2.2、3、4、0.5、1 kHz |

依据：`CPS_FM_INFO`（`02000078`）、`CPS_SW_INFO`（`02000079`），均 Pack=1；`wfm_fm..cctor`（`060004D0` / `0x7BBB8`）；`param_string.AgcList_Items`（`060002C6` / `0x4A430`）。BK1080 视图拒绝改写没有确认生效的 AM/SSB/AGC 字段。

### 每条 8 字节记录

| 偏移 | 类型 | 含义 |
|---:|---|---|
| `+0` | `u32le` | 频率，单位 10 Hz |
| `+4` | `u8` | 非 FM 频段解调：1=AM、2=LSB、3=USB |
| `+5` | `u8` | 保留；编辑其他字段时保持 |
| `+6` | `i16le` / 原始 `u16le` | 带符号 BFO / Hz，同时保留原始位模式，见下文 |

依据：`CPS_FM_FREQ_INFO`（`02000077`），字段 token `040006E9..040006EC`；转换器 `0600002A..0600002D`。读取频率除以 100000 得到 MHz，写回乘以 100000，因此确定为 10 Hz 存储单位。

清空预置采用把频率置 0 的 CPS 空单元格表示，并保留该记录的其他字节。读取时同时识别擦除态 `0xFFFFFFFF`，不会自动把擦除态转换为零。VFO 不作为可删除的预置台。

**BFO 已确认是带符号的 Hz。** CPS 的 `UInt16` 表示不能单独解决符号问题；本轮跟踪了 ENG 8.02.16 的实际接收器消费者，并以 34 组原 ARM 调用确认：16 位补码、有符号 Hz、向零归整到 10 Hz 后写 Si 属性 `0x0100`。编辑器提供 `-16380..16380 Hz`、10 Hz 步进，API 同时保留 `bfo_raw` 以供无损往返。原值超出编辑范围或不对齐时，修改其他字段仍保持原字节；只有更改 BFO 才验证新值。FM 视图不提供 BFO 或 AM/SSB 编辑器。详见 [BFO 证据](bfo.md)。

## 设置路径的新增交叉核对

`src/core/schema.mjs` 是独立描述的字段清单。`raw:true` 表示物理单位或完整枚举尚未证实，编辑器显示原始存储值；不是默认为毫秒、秒或其他产品的功能名称。

| 项目 | 新证据 | 处理 |
|---|---|---|
| APRS 发送间隔 | `CPS_APRS_Config.TxInterval` 是 `u8`，位于 `+3`；ACK 是 `+4` | 用 1 字节实现 CPS 路径；记录 APK 2 字节声明与 ACK 重叠，不覆盖 ACK |
| APRS filter | 转换器 `06000018/19` 使用 mask 1、2、4、8、16、32、64、128 | Position 是 bit0，依次至 Status bit7；单独修改位时保留其他位 |
| APRS 纬经度 | raw /10000 显示 `ddmm.mmmm` / `dddmm.mmmm` | 使用精确文本转换并校验分钟小于 60；不当作十进制度 |
| APRS 8 频率 | 读取 raw /100000 显示 MHz | 整数 Hz API，10 Hz 精度 |
| APRS 文本 | CPS 使用 ASCII 编码 | 禁止不能编码的字符，避免悄悄替换问号 |
| DTMF / 5TONE 分隔符、组码 | CPS 是固定 `byte[2]`，不是 UInt16 码值 | 按本字段允许字符集编辑单个 ASCII 符号，保留终止字节 |
| DTMF / 5TONE 联系人 | 读取转换器 `0600001B/1D` 均调用 `Util.IsAllDigits` (`0600026A`) | 联系人 ID 仅接受 0..9，最多 8 B；上/下线码可用的符号不能直接用于联系人 ID |
| 5TONE 自定义频率 | CPS 数组 `UInt16[15]`；APK 只声明前 14 项 | 保留并提供 15 个原始字值，不猜最后一项的音符标签 |
| 时区 | CPS Int16 保存选项索引 | 不把它当成有符号 UTC 分钟数 |
| 通话结束音 | APK 64 与 68 版本选项不同 | 保留 0..2 值，不转成布尔 |

APRS 结构 token `0200008F`，大小 256；主设置结构 `0200007B`，大小 296；Gen2 结构 `0200007C`，大小 112。

### 预制消息的 CPS / APK 差异

`CPS_PreDefineMesg`（`02000090`）是 256 字节：`+0 UInt32 idx`、`+4 byte[4]`、`+8 byte[16]`、`+24 byte[48] content`、`+72 byte[184]`。APK 将文本声明为 56 字节，与当前 CPS 的 48 字节不一致。本实现只编辑已证的 48 字节，并保留 `+72..+79` 及其他保留内容。

CPS 读取器 `ConvertCpsAprsPreDefineMSMParam`（`06000017` / `0x5BDC`）用 UTF-8 解码，再去除两端 NUL；写入器 `ConvertPreDefineMsm`（`060003F3` / `0x6956C`）却明确采用 ASCII。Web 读取有效 UTF-8，遇到无效编码时显示字节转义、保留完整原始记录；兼容写入限制为 48 字节 ASCII，避免 CPS 将中文替换为问号。这个限制不等于设备固件只能显示 ASCII，设备端文本消费者尚未重放核验。

该 CPS 读取器遇到第一个 `idx >= 64` 就停止。它的写入器把非空文本紧凑排列并生成 `idx = 0..n−1`。Web 的局部编辑不自动移动其他记录：`readMessage` 分别报告本槽 `valid` 和连续表中的 `cps_visible`；`active:true` 将本槽索引设置为槽号，`active:false` 写 `0xFFFFFFFF`，保留原文本。中间停用一个槽会使 CPS 看不到后续槽；单独修改文本不会隐式激活已删除记录。完整固件侧及 APK 行为仍应以后续实机/原函数验证为准。

### 频段组与开机图的具体剩余问题

频段组并非简单的“160 和 272 二选一”：`CPS_LOCK_FREQ_INFO`（`02000081`）解释了每槽前 160 字节；`LockFreq.GetData`（`0600004C` / `0x351AC`）和 `main.ConvertCpsLockFreq`（`060003D4` / `0x67D94`）均使用 **272 字节槽距、8 槽**，与 APK 一致。但 `CpsReadLockFreq`（`06000509` / `0x80098`）按 160 字节连续推进，构成 CPS 自身路径之间的不一致。后续已直接执行固件消费者确认 **272 字节**、连续 magic 前缀及选择规则，新增 `band-codec.mjs` 提供语义编辑并保留每槽尾部 112 字节；详见 [bands.md](bands.md) 和 [bands-replay.json](evidence/bands-replay.json)。

开机图结构 `CPS_PICTURE_INFO`（`02000087`）为：`+0 u32` magic `0x9ABC5A5A`、`+4 u16` 数据长度、`+6 byte[2]` 保留、`+8 byte[1024]` 位图，总 1032 字节。`genset.button8_Click`（`0600036D` / `0x5621C`）只接受 128×64 图像。`PictureConvert.ChangeScanDir`（`06000096`）把 BMP 底向上的行次序翻转，再用 `06000097` 的 MSB 像素抽取改成竖向页面字节；`Bmptobin`（`0600036E`）按黑白调色板统一为 1=黑。故图像内的 `(x,y)` 对应 `byte[(y>>3)*128+x]` 的 `1<<(y&7)`。

已经实现 `readStartupBitmap`、`patchStartupBitmap`、`pageBytesToPixels`、`pixelsToPageBytes`。新图片设置已证 magic 与 1024 长度，保留头部 `+6/+7`；四角、跨页像素及原始字节测试通过。stock CPU loader `0x0800FD04` 也已运行验证正确头部时复制 1024 字节、错误 magic 或长度时拒绝且保持输出缓冲区。图像位排列与文件读写已验证，面板上电显示仍未作实机验收。

开机密码存在专门 formatter、设备端有独立保护状态。当前只保留和读取该原始区，不提供猜测式密码或保护区改写。

## 保真编辑与验证

数据 API 返回新的 Uint8Array，不修改传入备份。未知字节、未知枚举、擦除态、非规范亚音在读取时原样保留；只对用户明确编辑的字段校验和修改。

普通信道名称编辑只覆盖固件实际使用的前 10 字节，保留 16 字节分配中的后 6 字节。严格 GB2312 字符表由 Python 标准编码器生成，避免浏览器 `TextDecoder('gb2312')` 实际接受更大 GBK 字集而造成不可逆写入。

Node 内置测试覆盖已知编码 fixture、10 Hz 精度、符号/溢出边界、GB2312/ASCII 拒绝、未知字节保持、广播 VFO 数量和芯片能力隔离、APRS 间隔冲突、filter 位序、ddmm 坐标及联系人/消息的局部改写。测试不冒充对真实设备的验收。

相关文件：`src/core/channel-codec.mjs`、`radio-codec.mjs`、`settings-codec.mjs`、`schema.mjs`；接口中的索引均从 0 起算，广播记录 0 的 VFO 是特别说明的例外。

### 本次 stock CPU 重放

[radio-replay.json](evidence/radio-replay.json) 记录 **24 组断言通过**。使用固定哈希参考镜像，在 Cortex-M0 指令仿真中执行实际函数，不用自写函数替代被测 loader/saver：

- `0x0800F020`：广播加载。Si4732 条件分别加载四个频段；BK1080 条件下即使 NOR 选择 SW 也强制 FM。全组验证真实 NOR 读取、32/128 预置拷贝和 VFO 字值。
- 此 loader 每次从选定银行读 **1040 B** 到临时缓冲，但 FM/LW/MW 只复制其中 32 个预置。不能用这个临时读取长度推断各 FM/LW/MW 银行占用 1040 B。
- `0x080101FC`：广播保存。4 个频段 × flags 0、1、2、3，验证全局头部写 8 B、前三组写 272 B、SW 写 1040 B，并逐字节比较整个合成 NOR，确认无关字节未变。
- `0x0800FD04`：开机图加载。有效头部、错误 magic、错误长度各一组，确认返回值及输出保留行为。

只替换底层 NOR read / sector erase / page program 三个硬件边界，实际校验、内存拷贝、RMW 指令仍执行。合成容量 4 MiB 是实验输入，没有因此新推定容量；没有模拟接收芯片、MMIO、显示面板、USB、BLE、RF 或物理时序。

复现需要独立取得参考镜像和既有研究仓库的 MIT 仿真辅助脚本：

```sh
python tests/reference/replay-radio.py /path/to/stock.raw.bin \
  --research-tools /path/to/uv-k10pro-firmware/tools \
  --output /path/to/radio-replay.json
```

此可选参考实验使用辅助仓库的 Unicorn 依赖；Web 应用与 Node 测试保持零第三方运行依赖。
